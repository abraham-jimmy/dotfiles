# Ideas To Tasks

Convert reviewed ideas from a manually edited change inbox into task files.

## Input

$ARGUMENTS: optional feature folder or inbox file

Recommended inbox file name:

- `.ai/<feature-slug>/change-inbox.md`

Use `change-inbox.md` for rough notes, desired changes, UI tweaks, follow-up ideas, and implementation feedback that should not interrupt the current work session.

Example inbox format:

```markdown
# Change Inbox

## Raw

- the homepage font feels wrong
- primary button color maybe warmer?
- spacing cards dashboard same as rules?

## Open

- [ ] Change the landing page font to feel less corporate.
- [ ] Make the primary button color warmer.
- [ ] Revisit whether the dashboard card spacing matches the design rules.

## Blocked

## Processed
```

The inbox may also contain plain bullets or short paragraphs. Do not require a strict format before refinement.
Prefer the `Raw`, `Open`, `Blocked`, and `Processed` sections when organizing the inbox.

## Resolution

1. If an inbox file is provided, use it.
2. If a feature folder is provided, use `<feature-folder>/change-inbox.md`.
3. If no argument is provided, resolve the Git root with `git rev-parse --show-toplevel`.
4. Search only under `<git-root>/.ai/` for `*/change-inbox.md`.
5. If exactly one inbox is found, use it.
6. If multiple inboxes are found, ask the user which one to process.
7. If no inbox is found, ask the user for the feature folder or inbox file path.

The feature folder is the parent folder of `change-inbox.md`.

## Process

1. Read `change-inbox.md`.
2. Do not create, update, or rewrite `T00-spec.md`.
3. Read sibling task files named `TNN-*.md` where `NN` is greater than `00`.
4. Only update incomplete task files named `TNN-*.md` where `NN` is greater than `00` and the file does not end in `-DONE.md`.
5. Preserve completed task files: do not recreate, overwrite, rename, or modify files ending in `-DONE.md` unless the user explicitly chooses to reopen them.
6. Run the `Refinement Gate` before task creation.
7. If refinement was needed and changed `change-inbox.md`, pause and ask the user to review the refined ideas before continuing.
8. Only continue to task creation after refinement changes if the user confirms.
9. Inspect the repository only as needed to confirm existing implementation, file paths, conventions, constraints, or design rules.
10. Triage only unprocessed inbox ideas under `## Open`. Ignore checked items and anything under `## Processed` unless the user explicitly asks to revisit them.
11. Create or update task files using the same structure and expectations as the task files generated by the `spec-to-tasks` command.
12. Do not implement application code. Stop after task files are updated unless the user explicitly asks to execute work.

## Refinement Gate

Before creating or updating task files, perform the same first check used by the `refine-ideas` command.

Refinement is needed if any of these are true:

- `## Raw`, `## Open`, `## Blocked`, or `## Processed` is missing.
- There are notes under `## Raw`.
- There are unsectioned notes outside the standard sections.
- `## Open` contains duplicate or overlapping ideas.
- One idea contains multiple unrelated changes.
- An idea is too vague to become a task without cleanup.
- An idea appears already covered by an existing task.
- Checked items remain under `## Open`.
- An idea needs a user choice or conflicts with known task direction.

If refinement is not needed, continue directly to task creation.

If refinement is needed:

1. Ensure `change-inbox.md` has `## Raw`, `## Open`, `## Blocked`, and `## Processed` sections.
2. Treat unchecked ideas under `## Raw`, unchecked ideas under `## Open`, and unsectioned notes as candidates for refinement.
3. Ignore anything under `## Processed` unless the user explicitly asks to revisit it.
4. Move checked items found outside `## Processed` to `## Processed`.
5. Deduplicate similar ideas.
6. Merge overlapping notes into one clearer idea.
7. Split bundled notes into separate ideas when they describe independent changes.
8. Rewrite unclear notes into concise actionable ideas without choosing product behavior, visual direction, architecture, dependencies, or scope.
9. Move every refined actionable idea to `## Open` as an unchecked item.
10. Move every unclear, conflicting, choice-dependent, or blocked idea to `## Blocked` with the question or blocker.
11. Move every already-covered idea and duplicate raw note to `## Processed` with `Duplicate of: [refined idea]` or `Covered by: TNN-<task-slug>.md` when relevant.
12. Preserve the original intent; do not delete ideas unless the user explicitly asks.
13. After updating the inbox, stop and ask the user to review the refined `## Open` and `## Blocked` sections before task creation.

If the user wants refinement only, stop after refinement and suggest `refine-ideas` for future inbox-only cleanup.

## Grouping Rules

- If multiple ideas can be implemented cleanly in one task, put them in one task.
- If one idea needs multiple implementation phases, split it into multiple tasks.
- Split tasks at natural commit boundaries, sequencing boundaries, ownership boundaries, or review boundaries.
- Keep each task independently workable when possible.
- Prefer updating an existing incomplete task named `TNN-*.md` where `NN` is greater than `00` when the idea clearly belongs there.
- Prefer creating a new task when adding the idea to an existing task would make it too broad, change its purpose, or hide a separate decision.
- Create new task files only after the highest existing numbered task in the feature folder, including completed tasks. For example, if `T01-setup-DONE.md` and `T03-polish.md` exist, create `T04-<task-slug>.md`, not `T02-<task-slug>.md`.
- Never create a duplicate task for work already covered by an incomplete task.

## Decision Rules

- If any choice is required, stop and ask the user which option to take.
- If an idea clashes with the current task scope, constraints, design decisions, design rules, or implementation direction, stop and ask the user how to proceed.
- If an idea affects completed work, ask whether to create a follow-up task, reopen the completed task, or move the idea to the appropriate inbox section.
- If an idea proposes a large scope change, new feature area, or major redesign, ask whether to keep it as follow-up work or run the `spec` command to create a new feature folder with the bigger scope.
- If an idea is ambiguous but can be clarified without changing intent or choosing a direction, rewrite it more clearly in the relevant task.
- If clarifying an idea would require choosing product behavior, visual direction, architecture, dependencies, or scope, ask the user first.
- Do not silently choose colors, fonts, layouts, copy tone, libraries, naming schemes, architecture, or scope tradeoffs.
- Do not assume priorities unless the inbox, existing tasks, or user explicitly states them.

## Inbox Updates

After accepted ideas are reflected in tasks:

1. Keep the original idea text visible.
2. Move every task-covered idea to `## Processed`.
3. Add `Covered by: TNN-<task-slug>.md` below each processed idea.
4. Move every unresolved, conflicting, or user-question idea to `## Blocked`.
5. Leave only unprocessed actionable ideas in `## Open`.

Do not delete inbox ideas unless the user explicitly asks.

## Task File Requirements

When creating a new task file, use the existing task format:

```markdown
# TNN: [Clear task title]

## Completed State

Status: Not completed

What was done:
- Nothing yet

## Summary

[1-2 sentences describing what this task delivers.]

## Depends on

- None

## Do

- [ ] [Concrete implementation step]
- [ ] [Concrete implementation step]

## Files

- `path/to/file` — [why it matters]

## Relevant Context

- [Only details needed for this task]

## Verify

- `command`
- Manual: [specific check]
```

## Review Check

Before finishing, verify:

- Every processed inbox idea is represented in an incomplete task file or a user-approved completed-task decision.
- `T00-spec.md` was not created, updated, rewritten, or renamed.
- Task files are concrete, scoped, and reviewable.
- Task files were created or updated only after the user confirmed the refined inbox.
- No completed `TNN-*-DONE.md` file was overwritten or regenerated.
- Checked items and ideas under `## Processed` were not processed again.
- Every handled idea was moved into exactly one of `## Open`, `## Blocked`, or `## Processed`.
- Any required user choices were asked instead of assumed.
- `change-inbox.md` clearly shows which ideas were processed and which remain blocked.

## Output

After writing:

1. Return the task files created or changed.
2. Summarize how ideas were grouped or split.
3. List unresolved questions or blocked ideas.
4. Briefly say how `change-inbox.md` was updated so future runs avoid duplicate work.
5. Suggest the next command, usually the task execution command against the next incomplete task.
